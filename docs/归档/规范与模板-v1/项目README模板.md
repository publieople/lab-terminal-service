## 一、项目概述

*用 3–5 句话说清：这是个什么东西、解决谁的什么问题、现在是什么状态（已完成 / 在用 / 半途而废 / 已下线）。读者只读这一段也应该知道要不要继续往下看。常见错误：从技术选型开始写，读完不知道项目是干嘛的；或者写成宣传语，"致力于打造高效可靠的一体化平台"。*

## 二、项目目标

*写成可验证的条目，每条都要能被判定为"达成了"或"没达成"。分清**当初定的目标**和**实际追求的边界**（不做什么也是目标，能防止项目无限膨胀）。常见错误：写"提升工作效率""优化用户体验"这类无法判定的目标；把实现手段（用 Docker 部署）当成目标写。*

## 三、技术路线

*画出从输入到输出的主链路：数据/请求从哪来、经过哪几个组件、到哪去。每个关键选型后面跟一句**为什么选它、为什么不选当时同样可行的另一个**——半年后别人质疑这个选型时，靠的就是这句话。常见错误：给出一张技术栈名词表（"Python + FastAPI + Redis"），既没有数据流也没有取舍理由。*

## 四、开发环境

*列出跑通这个项目所需的软件侧条件：操作系统与版本、运行时（语言、版本号）、依赖安装方式、数据库/中间件及其版本、需要开的端口。写出版本号，不要写"最新版"。常见错误：漏掉版本号导致复现时踩版本坑；把本机的绝对路径写进来（用 `<路径>` 占位）。*

## 五、硬件环境

*列出硬件侧条件：机器台数、CPU/内存/显存/磁盘的类型与下限、GPU 型号与驱动、需要的外设或边缘设备。写清哪些是"能跑起来的最低配"、哪些是"实际部署配置"。常见错误：一句"普通服务器即可"；写真实主机名或序列号（用 `<设备名>`、`<序列号>` 占位）。*

*没有独立硬件需求时：*

*不适用：本项目全部运行在已有的容器平台上，无额外硬件要求。*

## 六、核心代码

*只放**决定项目能不能成立的那几段**：关键函数、核心算法、必要的配置片段。每段代码前一句话说它解决什么问题，代码块标明语言，路径写成仓库内相对路径。常见错误：整文件粘贴当仓库备份用；代码没有上下文说明；粘了代码但配的注释是"初始化"。*

## 七、项目实现

*按时间或模块讲清"是怎么一步步做出来的"：每个阶段做了什么、遇到什么、怎么绕过去的。这一节是给复现者看的路线图，让他知道 §八 的命令是怎么来的。常见错误：把 §六 的代码在这里再讲一遍；只写成功路径，把中途放弃的方案删掉——被放弃的方案恰恰是后来人最容易重复踩的。*

## 八、复现步骤

**这一节是全文最关键的一节。** 判据只有一条：**一个从没参与过这个项目的人，只读这一节，能从零跑出一样的结果。** 做不到就是文档的错。

必须逐条回答下面六个子问题，每条都单独成小节。命令必须可复制粘贴执行，并标明**在哪台机器、什么目录、什么权限**下执行。

### 8.1 准备什么

*前置条件清单：需要几台机器、什么权限（sudo / root / 普通用户）、需要提前向谁申请什么（账号、端口、域名、算力配额）、需要提前拿到什么文件或数据。写清"没有它会卡在哪一步"。*

### 8.2 装什么

*逐条命令的安装步骤，带版本号。分系统写（Linux 发行版不同则分开），标明包管理器与是否需要联网。每条命令后面写预期输出或成功标志。*

### 8.3 配什么

*需要修改的配置文件、需要设置的环境变量、需要填的占位值。给出配置文件片段和**改哪一行**，不要只说"按需修改配置"。敏感值一律用 `<内网IP>`、`<用户名>` 这类占位符。*

### 8.4 跑什么

*启动/执行命令，以及先后顺序。有多个服务时写清启动顺序和依赖关系；给出用 `systemd`、容器还是前台运行的差别。*

### 8.5 预期结果

*贴真实的输出片段（脱敏后）、日志关键行、界面截图或接口返回示例。让复现者能拿自己的结果跟这里逐行对照。*

### 8.6 如何判定成功

*写出**具体的验证动作 + 通过标准**：跑哪条命令、看到什么算通过、看到什么算失败。失败时指向 §十「已知问题」里对应的条目。这一小节是复现者唯一能自己判断"我做对了没有"的依据，不能省。*

## 九、项目成果

*可度量的结果：完成了什么、指标是多少、谁在用、被谁引用过。用数字代替形容词。常见错误：写"效果良好""获得一致好评"。*

## 十、已知问题

*现在仍然存在、但本次没解决的问题，逐条写：现象 → 影响范围 → 临时绕过办法。这是接手人的第一份清单，写全比写好看重要。没有就写"不适用：目前未发现遗留问题"。*

## 十一、后续方向

*接下来可以做什么，按优先级或价值排序。每条写清"为什么值得做"和"需要什么前置条件"。写清哪些是**已经确认不做**的，避免下一任维护者重新论证一遍。*
