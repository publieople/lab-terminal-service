## 这个库是怎么组织的

内容分四条线，加两类管理页。规律很简单：**看文件在哪个目录，就知道它是哪一类。**

```text
学习/  → 按顺序学会一件事（路线图 + 一章一章）
参考/  → 一门技术一篇，用到时来查
项目/  → 我们做出来的东西，含完整复现步骤
经验/  → 一个坑一篇：现象、原因、怎么修
历史与交接/ → 人员、设备、系统的变动记录
部门根页面与各类 README、规范 → 管理页
```

每一页开头都有一段元信息（类型、维护人、更新日期、状态、难度、适用版本）。**`状态: 草稿` 的内容不要当成结论**；`状态: 待修订` 表示内容曾经可用，但现在已知过时。旧结构与旧规范已删除，git 历史里查得到。

每一类页面必须有哪些章节、front-matter 有哪些字段，见[知识库规范](规范/知识库规范.md)；本文提到的索引表都由脚本从 front-matter 生成。

## 两条边界

### 1. 公开库只放能公开的内容

这个仓库是**公开**的。凡是涉及内网地址、服务器台账、真实主机名与域名、账号与凭据位置的内容，都放在配套的内部库里。公开页面上会以「内部细节见内部库」的形式留一个提示。

判断标准只有一句：**这段内容落到外面人手里，会不会给实验室添麻烦。**

### 2. 内容不押注平台

本库的正文将来可能被要求整章并入实验室主书（现在用 MkDocs + GitHub Pages），所以这个库的做法是：

- 内容全是**纯 Markdown**，没有任何平台专有语法。
- 页面之间只用**相对路径**互链。
- **部门章是完全自包含的**：`docs/部门/终端服务部/` 里不出现任何指向章外的链接，于是它随时能整棵搬走，不会产生断链（见仓库根目录的 `并入主书说明.md`）。

仓库根目录同时提供了 MkDocs（`mkdocs.yml`）、GitBook（`SUMMARY.md` + `.gitbook.yaml`）和 LLM 读取（`docs/规范/知识库规范.md` + `_schema/pages.json`）三种入口，**换平台不需要动内容**。

## 怎么本地预览

```powershell
python -m venv .venv
.\.venv\Scripts\pip install -r requirements-docs.txt
.\.venv\Scripts\mkdocs serve
```

然后打开 `http://127.0.0.1:8000`。（这里写成代码块：链接检查工具会真的去连它，本地服务没起来就报断链。）
