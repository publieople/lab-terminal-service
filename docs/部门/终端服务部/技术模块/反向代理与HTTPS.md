# 反向代理与 HTTPS

> ⚠️ **本页是骨架**：§一、§二、§四 已写实，其余小节待补。缺口清单见[待补事实](../待补事实.md) E2。

## 一、技术是什么

**让多个 Web 服务共用一个入口端口，并按请求里的域名把它转发到正确的那个服务。**HTTPS 是在这之上再加一层加密与身份验证。

它替代的做法是"一个服务占一个端口，谁用谁记端口号"。那种做法在服务只有两三个时还行，超过之后必然出事——最典型的一种就是**某个服务悄悄占住了 80 端口，于是所有想用 80 端口的服务都表现异常，而它自己工作得完全正常**。

## 二、为什么使用

- **端口收敛**：对外只有一两个入口，端口分配这件事才有办法管。
- **一个地方管证书**：HTTPS 只在入口处配置一次，后面的服务不用各自处理。
- **故障隔离**：某个服务挂了，其他服务的访问不受影响。

### 在什么情况下不值得

| 情况 | 为什么不用 |
| --- | --- |
| 只有一个服务，且只在内网/组网内自用 | 直接用服务自己的端口 + 组网访问更简单 |
| 组网工具已经提供了 `serve` 一类的暴露能力 | 已经有一个入口了，再叠一层是重复 |
| 没有人手维护证书 | **证书过期会让所有服务一起不可用**，比各自暴露更糟 |

**必须讲清的限制**：把多个服务收到一个入口，意味着**这个入口成了单点**。所以入口本身要纳入[监控与备份](监控与备份.md)的巡检范围，否则你会得到一个"所有服务一起挂"的最坏情况。

## 四、使用环境

| 项 | 说明 |
| --- | --- |
| 反向代理 | 任选（实验室现状待补，真实清单在内部库） |
| 端口 | **80 端口已划为保留端口，不得再新增占用**，细节见内部库的端口登记表 |
| HTTPS 证书 | ⚠️ 本实验室组网所用的 tailnet **不支持签发 TLS 证书**（`tailscale cert` 会返回 `does not support getting TLS certs`），因此组网内暴露只能用明文 HTTP。要 HTTPS 就必须另想办法（自签证书或外部证书），**别在这条路上耗时间** |
| 组网暴露 | 见[Tailscale 组网](Tailscale组网.md) 的 `serve` 用法 |
