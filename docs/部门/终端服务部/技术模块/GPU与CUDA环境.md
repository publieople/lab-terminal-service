# GPU 与 CUDA 环境

> ⚠️ **本页是骨架**：§一、§二、§四、§七 已写实，其余小节待补。缺口清单见[待补事实](../待补事实.md) E2。

## 一、技术是什么

**让程序能用上 NVIDIA 显卡算力的一整套软件栈**，从下往上三层：

```text
显卡驱动（由显卡与系统版本决定）
    └─ CUDA 运行时（由驱动版本决定上限）
        └─ 深度学习框架（PyTorch 等，决定它要哪个 CUDA）
```

这三层的版本必须能对得上。**实验室里绝大多数"GPU 用不了"，都是这三层里有两层对不上，而不是显卡坏了。**

它替代的做法是"用 CPU 硬算"——在生成式与模型推理场景里，这个替代方案慢到没有实际意义。

## 二、为什么使用

实验室的生成式工作流、模型推理与部分 Agent 能力都依赖 GPU。这些任务的特点是**算力需求高、失败表现为"随机失败"**：环境错一点点，往往不是立刻报错，而是跑十分钟后 OOM，或者某些算子悄悄退回 CPU 跑到超时。

**所以 GPU 环境的问题要当成基础设施问题处理，不能当成"这次运气不好"。**

### 在什么情况下不值得

| 情况 | 为什么不用 |
| --- | --- |
| 任务本身很小（几百 MB 的模型、几十张图） | CPU 够用，占着 GPU 反而挡了别人的大任务 |
| 只是偶尔跑一次 | 让终端服务部代跑一次即可，不必自己配环境 |
| 开发阶段调逻辑 | 用小数据集在 CPU 上验证正确性，再上 GPU 跑规模 |

## 四、使用环境

| 项 | 说明 |
| --- | --- |
| 显卡 | NVIDIA（型号清单在内部库） |
| 驱动 | ⚠️ 版本以实际在用的为准，**不要写"最新版"**；升级驱动会影响所有依赖 GPU 的服务，属于🟡先问再做 |
| CUDA | `nvidia-smi` 右上角显示的 `CUDA Version` 是**这套驱动支持的最高版本**，**不是已安装的版本**——这是最常被误读的一处 |

| 隔离方式 | 容器（需显式申请 GPU）或宿主机直跑 |

## 七、常见问题

### 7.1 `Driver/library version mismatch`

```text
nvidia-smi: Driver/library version mismatch (NVML <版本>)
```

**表现**：`nvidia-smi` 直接报这一行，任何依赖 GPU 的任务随机失败。

**原因**：系统中的**内核态驱动**与**用户态库**版本不一致。最常见的触发方式是**驱动在后台被升级了，但机器还没重启**——新的用户态库已经装好，旧的内核模块还在内存里跑着。

**处理**：重启机器让内核模块与新库对齐。**重启前先确认没有别人正在跑 GPU 任务**（这是🟡先问再做的典型场景）。

> 这是实验室**已知且未修复**的问题，登记在[待补事实](../待补事实.md) D6。

### 7.2 `CUDA out of memory`

**排查顺序**（不要一上来就骂自己的模型）：

1. `nvidia-smi` 看**现在**是谁占着显存——经常是别人上一轮的任务没退出。
2. 确认没有残留进程后，再调小自己的 batch / 分辨率 / 精度。
3. 仍然 OOM 才怀疑模型与配置。

**判断要点**：如果显存是"刚好差一点"，通常是配置问题；如果是"差好几倍"，通常是**有别人的进程占着**。

### 7.3 容器里看不到 GPU

**表现**：容器内 `nvidia-smi` 找不到命令，或框架报 `no CUDA-capable device is detected`。

**原因**：容器默认看不到 GPU，需要显式申请；且宿主机的驱动版本必须满足容器内运行时要求。
