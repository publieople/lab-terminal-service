# 容器与编排

> ⚠️ **本页是骨架**：§一、§二、§四 已写实，其余小节待补。缺口清单见[待补事实](../待补事实.md) E2。

## 一、技术是什么

**把服务连同它的运行环境一起打包成一个可重复运行的单元（容器），并用一份声明式配置描述"它该怎么跑"（编排）。**

它替代的做法是"照着文档在一台服务器上手动装一遍"——那种做法的通病是：装完的机器和文档写的不一样、换一台机器就装不出来、同一台机器上两个服务互相改对方的依赖。

一句话判断：**容器的价值不在"轻量"，而在"每次跑起来的东西是一样的"。**

## 二、为什么使用

- **环境一致**：开发机上跑通的东西，服务器上大概率也能跑通。
- **可回滚**：出问题换回上一个镜像即可，不需要回忆"我改了哪几个文件"。
- **互不干扰**：一台机器上跑多个服务，不共享依赖。
- **可交接**：一份 `compose.yml` 就是一套能重跑的环境说明。

### 在什么情况下不值得

| 情况 | 为什么不用 |
| --- | --- |
| 单进程、无依赖、直接读写宿主机文件的小脚本 | 打包的成本高于收益，直接托管跑 |
| 需要直接访问特殊硬件的场景 | 设备映射与权限会变成新的坑；这类服务直接跑在宿主上更省事 |
| 只为了"显得规范"而把一切容器化 | 多了一层要维护的东西，出问题时排查路径反而更长 |

**代价要讲清楚**：容器引入了自己的网络模型和存储模型。实验室里最典型的两个后果是——**端口可能被容器抢先占用**（见[端口占用导致同域名本机访问 404](../技术经验/端口占用导致同域名本机访问404.md)），以及**数据忘mount在容器里，删容器等于删数据**。

## 四、使用环境

| 项 | 说明 |
| --- | --- |
| 运行时 | Docker Engine（版本待补） |
| 编排（单机） | Docker Compose v2（`docker compose`，不是 `docker-compose`） |
| 网络 | 部分服务使用 **host 网络模式**以直接暴露端口；这些服务的端口必须登记 |
| 数据 | 一律挂载到宿主机目录；**不允许数据只存在于容器可写层** |
