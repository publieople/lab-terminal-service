# Linux 服务器运维

> ⚠️ **本页是骨架**：§一、§二、§四 已写实，其余小节待补。哪些内容还缺、由谁补，见[待补事实](../待补事实.md) E2。

## 一、技术是什么

**在 Linux 服务器上让一个服务长期、无人值守地稳定运行所需的一整套日常动作。**

它替代的做法是"谁需要用谁就 SSH 上去手动跑一遍"——那种做法在只有一台机器、只有一个人用的时候还过得去，一旦机器变多、服务变多，就会变成"服务什么时候挂的没人知道、挂之前改过什么没人记得"。

严格说这不是一门技术，而是一组**约定 + 一组命令**。它之所以值得单独成篇，是因为实验室里绝大多数服务中断，原因都不是代码问题，而是这几件事没做：没有托管、没有日志、没有巡检、磁盘满了没人发现。

## 二、为什么使用

实验室的算力服务器、GPU 服务器、边缘设备几乎全是 Linux，而且**是无人值守的**：白天有人在上面跑实验，夜里和假期没人管。无人值守环境下，"服务在不在"不能靠人看，只能靠机制。

### 在什么情况下不值得

| 情况 | 为什么不用投入 |
| --- | --- |
| 一次性任务的机器（跑完就销毁） | 建托管和巡检的成本高于收益 |
| 只在一台机器上、只用几小时的临时服务 | 手动跑就够了，但**不要在共享服务器上占端口不释放** |
| 个人开发机 | 想跑就跑、想关就关，不属于本模块范围 |

判断标准是一条：**这个服务挂掉的时候，会不会有别人受影响？**会，就要托管 + 巡检；不会，可以不管。

## 四、使用环境

| 项 | 说明 |
| --- | --- |
| 发行版 | Ubuntu LTS 为主；部分实验机与 WSL 环境用 Arch |
| 服务管理 | systemd（`systemctl` / `journalctl`） |
| 登录方式 | SSH，**不使用默认 22 端口**（真实端口登记在内部库） |
| 远程组网 | 见[Tailscale 组网](Tailscale组网.md) |
| 权限 | 日常操作用普通用户 + `sudo`，不直接用 root 登录 |
