# 技术经验

**一个坑一篇。**这里放的是**真实发生过、并已经查清原因**的问题。

和[技术模块](../技术模块/README.md)的第七节「常见问题」的区别：

- **技术模块**里的常见问题 = **已知的、有标准答案的**现象（"连不上怎么办"）。
- **技术经验** = **当时不知道怎么办、花了不少时间才查清**的问题。重点在**为什么当初没想到**。

后者的价值在于：下次遇到**从来没见过的**故障时，读者从这里学到的是**排查的方法**。

---

## 为什么要写这一节

一个部门最贵的成本，是**同一个问题被不同的人各踩一次**。

而且踩坑的经验有个特性：**它天然只存在当事人脑子里。**技术文档有人写，坑没人愿意写——因为写坑等于承认自己卡住过，而且过程往往"不体面"（试了一堆错的方向）。

所以这一节的写作要求里有一条：**必须写"当时试过什么、为什么不对"**。那部分才是别人真正用得上的东西。只写"最终结论是加个互斥量"没有任何教育意义。

## 每篇该写成什么样

**六节固定结构**（现象 / 环境 / 原因 / 解决方案 / 验证 / 经验），其中三条是硬要求：

### 一、「现象」必须能被人认出来

写**症状**，不写结论。而且要包含**可以复制粘贴搜索的原文**——报错信息的原文、日志行的原文。转述过的报错搜不到。

反例：「服务启动失败」
正例：「服务能起来，日志停在 `Loading ... binding` 这一行不动了，进程不退出也不响应」

### 二、「原因」必须写到根因

停在第一个解释不算写完。**连着问三次"为什么"**：

```text
服务卡住了
  → 为什么？两个进程在抢同一个数据目录
    → 为什么会有两个进程？两个启动入口同时被触发
      → 为什么会同时触发？登录任务和健康探测的定时任务撞在一起了   ← 这才是根因
```

只写到第二层的话，解决方案会是"下次小心点"；写到第三层，解决方案才是"加一把锁"。**前者不是解决方案。**

### 三、「经验」必须能迁移到别的场景

不要写"下次记得先看日志"这种正确但没用的话。要写**可迁移的判断规则**：

- 「如果一个服务既可以被登录任务拉起、又可以被看门狗拉起，那它一定需要一把全局锁。」
- 「如果同一个域名在本机和外部表现不一致，先查本机有没有别的进程占了那个端口。」

判断标准：**读者遇到一个全新的、长得不一样的问题时，能不能用上这条经验？**
