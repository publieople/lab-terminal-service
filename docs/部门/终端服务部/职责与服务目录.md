# 职责与服务目录

这一页回答一个问题：**遇到具体的事，该谁做、能不能自己做、走什么流程。**

配套阅读：[部门介绍](README.md)（我们负责什么）、[待补事实](待补事实.md)（哪些还没定）。

---

## 一、三种处理方式

任何一件事，先判断它属于哪一档。**判断不清就按第三档处理**——多问一次的成本，远小于自己试坏的成本。

### 🟢 自助可做（看完文档直接做）

做错不影响别人、不需要审批、出问题能自己恢复的事。

- 在**自己的**账号下装软件、配自己的开发环境
- 读文档、查资料、在共享库里找现成的做法
- 自己机器上的组网客户端重连、服务重启
- 给自己的项目建目录、写文档、提 PR

### 🟡 先问再做（走 Issue，等回复）

影响**共享资源**或**其他人**的事。

- 占用 GPU / 长时间跑任务
- 在共享服务器上装系统级依赖、改全局配置
- 新增常驻服务、占用端口
- 改共享目录的权限
- 让某台机器对组网或公网暴露服务

### 🔴 必须走流程（不能自己动）

出错的后果超出单台机器或单个人。

- 改服务器**网络配置**（路由、防火墙、组网策略）
- 动**共享存储**（迁移、扩容、删除策略）
- 变更**访问控制**（谁能进哪台机器、哪个服务）
- 创建或删除**账号**、轮换**凭据**
- 让服务**对公网开放**
- 变更**备份策略**

> 🔴 类操作**没有"我先试试"这个选项**。试坏一次的恢复成本经常是几小时到几天，而且可能已经影响到别人。

## 三、一次服务请求的完整流程

```text
① 开 Issue（用「服务请求」模板填全要素）
        ↓
② 三个工作日内首次回复：排期 / 补充信息 / 说明为什么做不了
        ↓
③ 执行（🟡 与 🔴 都要有明确的负责人）
        ↓
④ 按事先约定的验收标准确认做完
        ↓
⑤ 回填文档：这次操作里有可复用的部分吗？有就写进【技术模块】或【技术经验】
```

**第 ⑤ 步是必做的。**如果跳过它，这个部门就会不断重复解决同一个问题，并且依赖记得住的人。判断一次服务请求做得值不值，看的正是第 ⑤ 步有没有产出。

### 请求被拒，通常会是因为

| 原因 | 怎么办 |
| --- | --- |
| 用途说明不清 | 补充"要做什么事"，需要的资源由我们据此判断 |
| 资源排不上 | 协商时间窗口，或说明为什么必须现在 |
| 有更简单的做法 | 按建议的做法走；如果确实不行，说明为什么不行 |
| 有安全或合规风险 | 与负责人一起设计一个可控的替代方案 |
| 不属于本部门 | 我们帮你转给对的人，或直接告诉你找谁 |

## 四、故障上报怎么写

**先说影响，再说现象。**顺序反了会让人判断不出紧急程度。

```text
【影响】哪些人/哪些项目现在做不了事？有没有波及正在跑的长任务？
【现象】什么时间开始的？之前做过什么改动？
【范围】一台设备还是一个服务？别人也遇到吗？
【已尝试】试过什么、结果如何
【原文】报错信息原文（不要转述）
```

**不要**只说"XX 用不了了"——那需要三轮追问才能开始处理。

**不要**在公开 Issue 里贴：内网 IP、主机名、账号名、报错里带的 token 或路径。转成描述性文字，需要细节时我们线下要。

## 五、值班与响应

| 场景 | 找谁 | 期望响应 |
| --- | --- | --- |
| 影响多人的服务中断 | 值班人（值班表待补） | 当日内 |
| 一般服务请求 | 对应职责负责人 | 三个工作日内首次回复 |
| 咨询与上手 | 文档优先 → 部门讨论群 | 一周内 |
| 安全事件（泄露、入侵迹象） | **部门负责人 + 指导老师**，同时停止相关服务 | 立即 |

> 时限与值班表以 [待补事实](待补事实.md) 补齐后为准。上面是拟定的约定，写在这里是为了**先有一个可以被讨论和被修改的对象**——没有约定的"尽快"到最后等于没有约定。
