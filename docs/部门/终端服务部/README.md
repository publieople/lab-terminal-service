# 终端服务部

**上海中侨大学 · 人工智能学院 · 具身智能研究所** —— 终端服务部

> **一句话定位**：我们负责实验室的**服务器与算力、网络与设备互联、Agent 平台与工具链、生成式工作流、边缘设备部署、账号与数据服务**——让实验室的算力、模型和设备，能被每个项目、每个人稳定地用起来。

这份文档是终端服务部的对外说明。**想知道我们能做什么、怎么找我们、新人从哪上手，读这一页就够。**

---

## 一、一句话定位

实验室的**核心支撑部门**——致力于构建和维护可靠的技术基础设施，同时推动知识管理和智能化工具的开发应用。

所属：**上海中侨大学 · 人工智能学院 · 具身智能研究所**。英文名 **Terminal Service Department**，部门口号 **Driving Infrastructure, Intelligence & Content**（英文名与口号取自部门既有材料，如需调整请直接改）。

其它部门的产出是算法、模型、硬件、论文；我们部门的产出是**让这些东西能跑起来的那个环境**——服务器不出事、网络连得通、模型跑得动、设备接得上、新人上手不用问人。

一个判断标准：**如果一件事的失败会让"整个实验室的很多项目同时做不下去"，那它就是我们的职责。**

## 二、职责范围

> **本节仍在确定中。**下面先保留部门既有的表述（三层核心价值 + 三项核心职能）；其中像"与宣传部协同运营社交媒体"这类条目是否仍由本部门承担，正在部门内部讨论。**要确认边界，请直接问部门负责人，不要照本节自行推断。**

### 2.1 三层核心价值

| 层次 | 一句话 |
| --- | --- |
| **稳定器** | 服务器 / NAS / 门户的稳定运行与安全防护 |
| **创新引擎** | AI 智能体与知识管理系统的研发落地 |
| **放大器** | 技术赋能社交媒体，打造实验室技术影响力 |

### 2.2 核心职能

#### 基础设施运维

- 服务器和 NAS 的日常运维与管理
- 门户网站的建设、维护和优化
- 系统监控与故障排查

#### 知识管理与创新

- 知识库的构建与维护
- 智能体（AI Agent）的开发与应用
- 技术文档的整理与沉淀

#### 平台运营与内容创作

- 与宣传部**协同运营**社交媒体平台（微博、微信公众号、抖音等）
- 技术内容的策划、创作与发布
- 品牌形象建设与对外宣传
- 社媒内容的技术支撑与后台管理

### 2.3 按技术方向的细分

上面前两项职能落到技术层面是六个方向。每个方向写清"做什么、交付什么、不管什么"——**边界比职责本身更重要**，因为边界决定了你该找谁、不该找谁。

六块，按"出事的杀伤半径"从大到小排列。

#### 方向 1 · 服务器与算力

**做什么**：物理服务器、GPU 工作站的系统安装与维护；算力资源的分配与排队；存储与备份；虚拟化与容器平台。

**交付物**：可登录的机器、明确的资源分配方案、可恢复的备份。

**边界**：不负责具体项目的训练脚本调优——那是项目自己的事，我们负责机器是好的、依赖装得上。

#### 方向 2 · 网络与设备互联

**做什么**：实验室内网与跨地点组网；设备之间的互访；内网服务的对外安全暴露；远程访问。

**交付物**：设备能互相 ping 通、能直连访问服务、外网能安全进门。

**边界**：不负责校园网的线路与出口——那是学校网络中心的事，我们负责实验室这一侧。

#### 方向 3 · Agent 平台与工具链

**做什么**：Agent 运行平台（会话常驻、任务编排、统一管理入口）的部署与维护；开发工具链（编辑器、CLI、插件）的推荐与规范化；共享知识与技能库。

**交付物**：一套"领了任务就能干活"的开发环境；一份写得清楚的选型说明（为什么选它、备选是什么）。

**边界**：不做业务逻辑，不替项目写 Agent 的提示词。

#### 方向 4 · ComfyUI 与生成式工作流

**做什么**：ComfyUI 及其模型的部署、显存与队列调优、常用工作流模板、模型文件的统一存放。

**交付物**：一个打开就能跑的界面，加一份"先装什么、放哪里、出问题先看哪里"的说明。

**边界**：不负责创作本身。

#### 方向 5 · 边缘设备 Agent 部署

**做什么**：把 Agent 与推理能力放到 MCU、单板计算机、嵌入式 AI 设备上；设备与主控之间的连接与协议；现场部署与自启动。

**交付物**：能自动拉起、断线能重连、日志能回收的边缘端。

**边界**：不负责机械结构与电路设计。

#### 方向 6 · 账号权限与数据服务

**做什么**：服务器账号、共享目录权限、服务凭据的**存放位置与归属**管理；数据目录规范；共享知识库。

**交付物**：谁有什么权限是说得清的；凭据有明确的保管人和轮换方式。

**边界**：**我们保管凭据的"位置说明"，不保管明文**。所有密钥、口令一律不入文档仓库（公开库和内部库都不放明文）。

## 四、服务对象与对接方式

### 谁可以找我们

- 本实验室的**项目组与课程**：算力、服务器、组网、Agent 平台、ComfyUI、边缘设备。
- 本实验室**个人成员**：账号开通、开发环境、上手协助。
- **其它部门**：与本部门职责交叉的部分（见第七节）。

### 怎么找

**统一入口：在知识库仓库开一个「服务请求」Issue。**（仓库地址见第九节）

不要把需求发在群里或口头提。原因不是官僚，是**口头需求一定会漏**：没人记录、没人跟踪、做完没人回填文档，下一个遇到同样问题的人还得再问一遍。Issue 是能搜索、能追踪、能沉淀的。

### 一份好的服务请求包含什么

| 要素 | 说明 |
| --- | --- |
| 请求类型 | 服务器与算力 / 网络与设备互联 / Agent 平台 / ComfyUI / 边缘设备 / 账号权限 |
| 申请人 | 姓名 + 所属项目或课程 |
| 需求描述 | **要做什么事**，不是"要一台服务器"。说清用途，我们才能给对规格 |
| 时间期望 | 本周内 / 两周内 / 可排期 |
| 验收标准 | 怎么算做完了。例如"能在组网内访问到某服务" |

> **不要在 Issue 里写内网 IP、密码、密钥。**需要这些信息的，我们线下对接。

### 响应约定

| 紧急程度 | 期望响应 | 说明 |
| --- | --- | --- |
| 影响多人的服务中断 | 当日内响应 | 直接找值班人，别只开 Issue |
| 一般请求 | 三个工作日内首次回复 | 给出排期或说明为什么排不上 |
| 咨询与上手 | 一周内 | 能自己解决的优先引导到知识库 |

以上是拟定的约定；**正式的响应时限**还在定，见 [待补事实](待补事实.md) 的 A6。

## 五、现有资源与能力清单（脱敏）

> **真实的设备台账（主机名、地址、端口、归属人）在内部库，不在公开库。**公开库只说明"我们有什么类型的能力"，不说明"具体是哪台机器"。这是为了不给实验室添麻烦——一台机器的地址泄露出去，风险不在于它本身值钱，而在于它是一扇门。

### 算力与服务器

- **通用服务器**：Linux 为主，承担常驻服务、数据存储、内部系统。
- **GPU 工作站 / 带 GPU 的服务器**：承担模型训练与推理、生成式工作流。
- **Windows 工作站**：承担需要图形界面或 Windows 生态工具的任务。

### 组网与访问

- 跨地点、跨网络环境的**设备组网**，使实验室的设备之间能直连互访，不必暴露公网端口。
- **子网路由**：让组网设备访问到实验室内网的整段地址，无需逐台配置。
- **内部 Web 服务的统一入口**：带访问控制，避免把服务直接挂到公网。

### Agent 与工具链

- 一台共享的 **Agent 会话常驻环境**，让长任务在断开连接后仍能继续。
- 一套**实验室共享的知识与技能库**（可被 Agent 直接调用的技能集合、共享记忆）。
- 常用开发工具链的推荐清单与安装方式（见[技术模块](技术模块/README.md)）。

### 生成式工作流

- ComfyUI 部署实例、统一的模型存放位置、常用工作流模板。

### 边缘设备

- 单板计算机与嵌入式 AI 设备若干，用于现场推理与设备接入的验证。

### 能覆盖的技术面

| 领域 | 能力 |
| --- | --- |
| 系统 | Linux 服务器安装、用户与权限、服务托管、日志与排障 |
| 容器 | Docker 与编排基础、镜像与数据卷、容器网络 |
| 网络 | 组网、子网路由、反向代理、HTTPS、端口与防火墙 |
| 算力 | NVIDIA 驱动与 CUDA 环境、显存与任务排队 |
| Agent | Agent 平台部署、连接器接入、会话常驻、技能库 |
| 生成式 | ComfyUI 部署与调优、模型管理 |
| 边缘 | 嵌入式设备接入、断线重连、自启动 |
| 运维 | 定时巡检、健康探测、告警、备份与恢复 |

## 八、新人上手路径

给刚进部门的人。**按顺序走，不要跳。**

```text
第 0 步  读完本页 + 《职责与服务目录》，知道这个部门在干什么、边界在哪
   ↓
第 1 步  拿到账号：服务器登录、组网接入、共享知识库
   ↓
第 2 步  读【基础知识】，补齐每天都会用到的概念
   ↓
第 3 步  按【技术模块】动手：先"Linux 服务器运维"，再"Tailscale 组网"，再选一个方向深入
   ↓
第 4 步  跟一个【项目实践】做一遍，从零复现到跑通（重点看那一节的"复现步骤"）
   ↓
第 5 步  读【技术经验】，看别人踩过的坑——这一步最省时间
   ↓
第 6 步  自己写第一篇文档：把刚踩的坑按【技术经验】的六节格式记下来
```

**第 6 步才是"入门完成"的标志**，不是第 5 步。因为能复现别人的东西只是会用；能把自己的经验写成别人能复现的东西，才算能给这个部门添砖。

新人最常问的三个问题，答案：

| 问题 | 答案 |
| --- | --- |
| "这个操作我不敢做，怕弄坏" | 先看在不在[服务目录](职责与服务目录.md)的"自助可做"栏；不在就开 Issue，**不要试** |
| "文档里没写怎么办" | 说明文档有缺口。做完之后**把缺口补上**，这是你能做的最有价值的事 |
| "某个服务挂了找谁" | 看[职责与服务目录](职责与服务目录.md)的负责人栏，找不到就找部门负责人 |
