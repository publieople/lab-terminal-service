# 终端服务部

**上海中侨大学 · 人工智能学院 · 具身智能研究所** —— 终端服务部

> **一句话定位**：我们负责实验室的**服务器与算力、网络与设备互联、Agent 平台与工具链、生成式工作流、边缘设备部署、账号与数据服务**——让实验室的算力、模型和设备，能被每个项目、每个人稳定地用起来。

---

## 一、一句话定位

实验室的**核心支撑部门**：负责构建和维护可靠的技术基础设施，也推动知识管理与智能化工具的开发应用。

所属：**上海中侨大学 · 人工智能学院 · 具身智能研究所**。英文名 **Terminal Service Department**（2026-10-15 正式采用），部门口号 **Driving Infrastructure, Intelligence & Content**。

产出是**让实验室的技术能跑起来的那个环境**：服务器不出事、网络连得通、模型跑得动、设备接得上、新人上手不用问人。判断标准只有一条：**如果一件事的失败会让「整个实验室的很多项目同时做不下去」，那它就是我们的职责。**

### 我们默认这么做

> 下面是**建议**，不是规定。写在这里是因为它们决定了我们默认怎么判断一件事该不该做、怎么算做完。

1. **Agent 能解决的让 Agent 解决；解决不了的，先想办法让 Agent 能解决。** 同一套手工操作重复三遍以上，就值得写成脚本，或者写成一条 Agent 能跑的工作流。写不出来，通常说明流程还没想清楚。
2. **能一条命令的不点十下鼠标，能自动的不靠人盯。** 巡检、备份、发布都该是脚本，而不是「记得去做」。
3. **先复现，再动手。** 修之前先能复现，改完再复现一次。没复现过的「修好了」不算修好。
4. **一次弄通，就写下来。** 做完当天写，别等下次再想一遍；写不出来，说明这件事还没真弄懂。
5. **不确定就说不确定。** 没验证的结论标「待验证」，不要和事实混在一起。下判断之前先看日志、看监控，别先猜。

## 二、职责范围

> **本节仍在确定中。**下面先保留部门既有的表述（三层核心价值 + 三项核心职能）；其中像「与宣传部协同运营社交媒体」这类条目是否仍由本部门承担，正在部门内部讨论。**要确认边界，请直接问部门负责人，不要照本节自行推断。**

### 2.1 三层核心价值

| 层次 | 一句话 |
| --- | --- |
| **稳定器** | 服务器 / NAS / 门户的稳定运行与安全防护 |
| **创新引擎** | AI 智能体与知识管理系统的研发与部署 |
| **放大器** | 用技术内容支撑社交媒体运营，扩大实验室的技术影响力 |

### 2.2 核心职能

- **基础设施运维**：服务器和 NAS 的日常运维、门户网站的建设与维护、系统监控与故障排查。
- **知识管理与创新**：知识库的构建与维护、智能体（AI Agent）的开发与应用、技术文档的整理与归档。
- **平台运营与内容创作**：与宣传部**协同运营**社交媒体（微博、微信公众号、抖音等）、技术内容的策划与发布、品牌形象建设与对外宣传、社媒内容的技术支撑与后台管理。

六个方向各自对应一页参考文档，具体需求与流程见[职责与服务目录](职责与服务目录.md)。

| 方向 | 管什么 | 边界 | 从哪页看起 |

## 四、服务对象与对接方式

### 谁可以找我们

- 本实验室的**项目组与课程**：算力、服务器、组网、Agent 平台、ComfyUI、边缘设备。
- 本实验室**个人成员**：账号开通、开发环境、上手协助。
- **其它部门**：与本部门职责交叉的部分（见第七节）。

### 怎么找

**统一入口：在知识库仓库开一个「服务请求」Issue。**（仓库地址见第九节）

不要把需求发在群里或口头提。原因是**口头需求一定会漏**：没人记录、没人跟踪、做完没人回填文档，下一个遇到同样问题的人还得再问一遍。Issue 能搜索、能追踪，讨论和结论都留得下来。

### 一份好的服务请求包含什么

| 要素 | 说明 |
| --- | --- |
| 请求类型 | 服务器与算力 / 网络与设备互联 / Agent 平台 / ComfyUI / 边缘设备 / 账号权限 |
| 申请人 | 姓名 + 所属项目或课程 |
| 需求描述 | **要做什么事**。写「要一台服务器」看不出用途。说清用途，我们才能给对规格 |
| 时间期望 | 本周内 / 两周内 / 可排期 |
| 验收标准 | 怎么算做完了。例如「能在组网内访问到某服务」 |

> **不要在 Issue 里写内网 IP、密码、密钥。**需要这些信息的，我们线下对接。

### 响应约定

紧急情况直接找值班人，别只开 Issue；一般请求、咨询与上手的响应时限见[职责与服务目录](职责与服务目录.md)的五、值班与响应。**正式时限还在定**，见内部台账 的 A6。

## 五、现有资源与能力清单（脱敏）

> **真实的设备台账（主机名、地址、端口、归属人）只放在内部库。**公开库说明「我们有什么类型的能力」，「具体是哪台机器」留在内部库。这是为了不给实验室添麻烦——一台机器的地址泄露出去，风险在于它是一扇门。

### 有什么

- **服务器与算力**：通用 Linux 服务器（常驻服务、数据存储、内部系统）、GPU 工作站（训练与推理）、Windows 工作站（图形界面与 Windows 生态工具）。
- **组网与访问**：跨地点组网、子网路由（不必逐台配置就能访问内网整段地址）、带访问控制的内部 Web 服务统一入口（不必把服务直接挂到公网）。
- **Agent 与工具链**：共享的会话常驻环境（断开连接后长任务仍能继续）、共享知识与技能库（可被 Agent 直接调用的技能集合与共享记忆）、常用开发工具链清单（见[参考](参考/README.md)）。
- **生成式工作流**：ComfyUI 部署实例、统一的模型存放位置、常用工作流模板。
- **边缘设备**：单板计算机与嵌入式 AI 设备若干，用于现场推理与设备接入的验证。
- **能覆盖的技术面**：Linux 服务器安装、用户与权限、服务托管、日志与排障；Docker 与编排基础、镜像与数据卷、容器网络；组网、子网路由、反向代理、HTTPS、端口与防火墙；NVIDIA 驱动与 CUDA 环境、显存与任务排队；Agent 平台部署、连接器接入、技能库；ComfyUI 部署与调优、模型管理；嵌入式设备接入、断线重连、自启动；定时巡检、健康探测、告警、备份与恢复。

## 八、新人上手路径

按顺序走，不要跳：

1. 读完本页与[职责与服务目录](职责与服务目录.md)，知道部门在干什么、边界在哪。
2. 拿账号：服务器登录、组网接入、共享知识库。
3. 按[学习路径](学习/学习路径.md)补概念，再按[参考](参考/README.md)动手：先 [Linux 服务器运维](参考/Linux服务器运维.md)，再 [Tailscale](参考/Tailscale/README.md)，然后选一个方向深入。
4. 跟一个[项目](项目/README.md)从零复现到跑通。
5. 读[经验](经验/README.md)，看别人踩过的坑，这一步最省时间。
6. 写第一篇文档：把刚踩的坑按经验页的六节格式记下来。**这一步做完才算入门。**

新人最常问的三个问题：

| 问题 | 答案 |
| --- | --- |
| 这个操作不敢做，怕弄坏 | 先查[服务目录](职责与服务目录.md)是否属于「自助可做」；不在就开 Issue，不要试 |
| 文档里没写怎么办 | 说明文档有缺口，做完之后把缺口补上 |
| 某个服务挂了找谁 | 查[职责与服务目录](职责与服务目录.md)的「谁处理」栏 |
